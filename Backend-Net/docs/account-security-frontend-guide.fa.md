# راهنمای فرانت: امنیت حساب‌ها (۲۰۲۶-۱۰-۰۴)

این سند می‌گوید بعد از تغییرات امنیتی بک‌اند، فرانت چه کاری **باید** بکند. قرارداد کامل API در `api-guide.fa.md` (بخش ۱، ۲، ۳ و جدول ۲۰۲۶-۱۰-۰۴ در بخش ۱۶) آمده است؛ اینجا فقط کارهای فرانت است، به ترتیب اولویت.

خلاصه‌ی تغییرات سرور:

- `ForgetPassword` حذف شد. رمز فراموش‌شده را مدیر با `ResetUserPassword` بازنشانی می‌کند.
- کسی که رمزش بازنشانی شده، تا رمز را خودش عوض نکند، هیچ کار دیگری نمی‌تواند بکند.
- ورود **تک‌نشستی** است: ورود دوم، نشست اول را فوراً می‌بندد.
- رمز اشتباه زیاد ⇒ قفل موقت (۴۲۹).
- مدیر نمی‌تواند روی حساب کسی کار کند که دسترسی‌ای دارد که خودش ندارد (۴۰۳).

---

## ۱. صفحه‌ی تغییر رمز عبور (الزامی، هنوز وجود ندارد)

الان در فرانت هیچ فرمی برای `PUT api/User/ChangePassword` نیست. این صفحه حالا ضروری است، چون کارمندی که رمزش بازنشانی شده بدون آن عملاً قفل می‌ماند.

**مسیر پیشنهادی:** یک route محافظت‌شده مثل `/profile/change-password` (به `ROUTES` اضافه شود). از منوی کاربر در هدر هم در دسترس باشد.

**بدنه‌ی درخواست:**
```json
{ "oldPassword": "Temp1234!", "password": "New1234!", "rePassword": "New1234!" }
```

**اعتبارسنجی سمت فرانت** (همان قوانین سرور، از `shared/lib/validationRules.js`):

- رمز جدید حداقل ۸ کاراکتر و شامل حرف انگلیسی، عدد و یک کاراکتر خاص باشد.
- `rePassword` با `password` یکی باشد.
- **جدید:** رمز جدید با رمز فعلی یکسان نباشد. سرور در این حالت ۴۰۰ می‌دهد با پیام «رمز عبور جدید باید با رمز عبور فعلی متفاوت باشد.»

**⚠️ مهم‌ترین نکته — پاسخ موفق توکن تازه دارد:**

```json
{ "data": { "accessToken": "eyJ...", "refreshToken": "...", "mustChangePassword": false }, "message": "...", "responseMessageType": "Success" }
```

تغییر رمز **همه‌ی** توکن‌های قبلی را باطل می‌کند، حتی توکنی که همین درخواست با آن رفته. پس در `onSuccess`:

```js
// features/auth/services/queries.js (پیشنهادی)
export function useChangePasswordMutation() {
  const setTokens = useAuthStore((s) => s.setTokens);
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: changePassword, // PUT /User/ChangePassword
    onSuccess: ({ accessToken, refreshToken }) => {
      setTokens(accessToken, refreshToken);
      // پرچمِ «تغییر رمز اجباری» (بند ۲) پاک می‌شود
      useAuthStore.getState().setMustChangePassword(false);
      queryClient.invalidateQueries(); // کوئری‌هایی که با ۴۰۳ شکست خورده بودند دوباره اجرا شوند
    },
  });
}
```

اگر توکن‌ها جایگزین نشوند، درخواست بعدی ۴۰۱ می‌گیرد. interceptor بعد سعی می‌کند با refreshToken قدیمی رفرش کند، که آن هم باطل شده است، و کاربر به صفحه‌ی ورود پرتاب می‌شود.

بعد از موفقیت: toast موفقیت، و اگر کاربر در حالت اجباری بود، رفتن به داشبورد (یا مسیر `from`).

## ۲. تغییر رمز اجباری بعد از بازنشانی توسط مدیر (الزامی)

### سرور چه می‌فرستد

پاسخ `Login` (و `RefreshToken`) فیلد جدیدی دارد:

```json
{ "accessToken": "...", "refreshToken": "...", "mustChangePassword": true }
```

پیام همین پاسخ هم فرق می‌کند: «رمز عبور شما توسط مدیر بازنشانی شده است؛ لطفاً پیش از ادامه، رمز عبور جدیدی برای خود انتخاب کنید.»

تا وقتی رمز عوض نشده، سرور **هر** درخواستی به‌جز این چهار را رد می‌کند:

| مجاز در حالت اجباری |
|---|
| `PUT api/User/ChangePassword` |
| `GET api/User/GetUserInfo` |
| `GET api/Permission/GetMyPermissions` |
| `POST api/Account/Logout` |

پاسخ رد شدن:

```http
HTTP/1.1 403 Forbidden
```
```json
{ "data": { "mustChangePassword": true }, "message": "رمز عبور شما توسط مدیر بازنشانی شده است. برای ادامه‌ی کار، ابتدا از صفحه‌ی پروفایل رمز عبور جدیدی برای خود انتخاب کنید.", "responseMessageType": "Danger" }
```

Refresh کمکی نمی‌کند، چون توکن تازه هم همین وضعیت را دارد.

### فرانت چه کند

1. **`authStore`:** یک فیلد `mustChangePassword` اضافه کنید که در `partialize` هم ذخیره شود (تا با رفرش صفحه از دست نرود)، به همراه `setMustChangePassword`.
   - `loginSuccess` و `setTokens` مقدارش را از پاسخ بگیرند.
   - `logout` آن را `false` کند.
2. **`useLoginMutation`:** `mustChangePassword` را هم به `loginSuccess` بدهید. در `LoginPage` → `onSuccess`، اگر `true` بود به‌جای `from`/داشبورد به صفحه‌ی تغییر رمز بروید و پیام سرور را نشان دهید (نه «خوش آمدید»).
3. **interceptor پاسخ (`shared/services/api/axios.js`):** ۴۰۳ با `data.mustChangePassword === true` را تشخیص دهید:
   ```js
   const body = error.response?.data;
   const forcedChange = status === 403 && (body?.Data ?? body?.data)?.mustChangePassword === true;
   if (forcedChange) {
     useAuthStore.getState().setMustChangePassword(true);
     if (window.location.pathname !== ROUTES.CHANGE_PASSWORD) {
       window.location.href = ROUTES.CHANGE_PASSWORD;
     }
   }
   ```
   این‌طوری اگر کاربر با یک تب قدیمی یا لینک مستقیم وارد شد، باز هم به صفحه‌ی درست می‌رود.
4. **گارد مسیر (`protectedLoader`/`AppLayout`):** وقتی `mustChangePassword` برقرار است، هر مسیری جز صفحه‌ی تغییر رمز به آن صفحه redirect شود. داخل این حالت:
   - منوی کناری و داشبورد نمایش داده نشوند، چون همه‌ی کوئری‌هایشان ۴۰۳ می‌گیرند.
   - فقط فرم تغییر رمز و دکمه‌ی خروج بماند.
   - `GetUserInfo` کار می‌کند، پس نام کاربر را می‌شود نشان داد.
5. در حالت اجباری **فیلد «رمز فعلی» را همان رمز موقتی بگیرید که مدیر داده**. در فرم یک خط توضیح بگذارید: «رمز موقتی که مدیر به شما داده را وارد کنید».

## ۳. ورود و خطاهای جدید آن (الزامی)

`LoginPage` الان هر خطا را با `getErrorMessage(error, …)` نشان می‌دهد و پیام سرور مقدم است. این کار درست است و ادامه‌اش دهید. نکته‌های تازه:

| وضعیت | کد | پیام سرور | پیشنهاد UI |
|---|---|---|---|
| نام کاربری یا رمز اشتباه | ۴۰۴ | «نام کاربری یا رمز عبور اشتباه است.» در ۳ تلاش آخر: «… تنها N بار دیگر می‌توانید تلاش کنید؛ پس از آن حساب شما به مدت ۵ دقیقه قفل می‌شود.» | پیام سرور را کامل نشان دهید؛ هشدار تعداد تلاش‌ها از همین متن می‌آید |
| حساب قفل است (۱۰ اشتباه پشت سر هم) | **۴۲۹** | «به دلیل ۱۰ بار ورود ناموفق، حساب کاربری شما موقتاً قفل شده است. لطفاً N دقیقه دیگر …» + `data.remainingSeconds` | پیام + شمارش معکوس از `remainingSeconds`؛ دکمه‌ی ورود تا پایان شمارش غیرفعال باشد |
| تلاش زیاد از یک شبکه (بیش از ۶۰ در دقیقه) | **۴۲۹** | «تعداد تلاش‌های ورود از این شبکه …» + `data.remainingSeconds` + هدر `Retry-After` | مثل ردیف قبل |
| کاربر غیرفعال | ۴۰۰ | «کاربر مورد نظر فعال نمی باشد» | بدون تغییر |

- `shared/lib/errorMessage.js` برای ۴۲۹ از قبل متن پیش‌فرض دارد؛ چون پیام سرور مقدم است، نیازی به تغییرش نیست.
- در حین قفل، **حتی رمز درست هم پذیرفته نمی‌شود.** بازنشانی رمز توسط مدیر قفل را فوراً باز می‌کند؛ اگر بخواهید، این را در پیام UI هم بگویید.
- **لینک «فراموشی رمز؟»** الان toast «برای بازیابی رمز با مدیر سیستم تماس بگیرید» نشان می‌دهد. این دقیقاً رفتار درست است و نیازی به تغییر ندارد. هیچ صفحه‌ای نباید `Account/ForgetPassword` را صدا بزند، چون این endpoint حذف شده و ۴۰۴ می‌دهد. متن `shared/lib/validationRules.js` (خط ۸) هنوز از `ForgetPassword` نام می‌برد و باید اصلاح شود.

## ۴. تک‌نشستی (توصیه‌شده)

هر ورود موفق، نشست قبلی همان کاربر را **فوراً** می‌بندد. درخواست بعدی آن نشست ۴۰۱ می‌گیرد. رفرشش هم ۴۰۰ می‌گیرد، چون refreshToken قبلی هم باطل شده است. همین اتفاق بعد از این موارد هم می‌افتد:

- خروج
- تغییر رمز در دستگاه دیگر
- بازنشانی رمز توسط مدیر
- غیرفعال/حذف شدن کاربر
- `LogoutUserById` توسط مدیر

interceptor فعلی این را درست مدیریت می‌کند: رفرش با ۴۰۰ رد می‌شود ⇒ `logout()` ⇒ رفتن به صفحه‌ی ورود. فقط **پیام** گم می‌شود و کاربر نمی‌فهمد چرا بیرون افتاده. پیشنهاد:

- در بلوک `catch` رفرش، قبل از redirect یک پرچم بگذارید (مثلاً `sessionStorage.setItem("sessionEnded", "1")`).
- `LoginPage` آن را بخواند و یک بار نشان دهد: «نشست شما پایان یافت؛ ممکن است با همین حساب از دستگاه دیگری وارد شده باشید یا رمز عبورتان تغییر کرده باشد. لطفاً دوباره وارد شوید.»

چند تب در **یک مرورگر** مشکلی ندارند، چون توکن مشترک دارند (`auth-storage` در localStorage و listener بین تب‌ها از قبل هست). فقط ورود از **مرورگر یا دستگاه دیگر** نشست قبلی را می‌بندد.

## ۵. صفحه‌ی کاربران: بازنشانی رمز و ۴۰۳ جدید (الزامی، کم‌حجم)

**`ResetPasswordDialog`:**

- بعد از موفقیت، پیام سرور را نشان دهید. الان: «رمز‌عبور کارمند با موفقیت بازنشانی شد؛ کارمند در اولین ورود باید رمز عبور جدیدی برای خود انتخاب کند.»
- در خود دیالوگ یک خط راهنما بگذارید: «کارمند با این رمز وارد می‌شود و بلافاصله باید رمز خودش را انتخاب کند. اگر حسابش به‌خاطر رمز اشتباه قفل شده باشد، قفل هم باز می‌شود.»

**قاعده‌ی زیرمجموعه:**

- این endpointها روی کاربری که دسترسی‌ای دارد که مدیر جاری ندارد، ۴۰۳ می‌دهند: `ResetUserPassword`، `UpdateUser`، `DeleteUser`، `ChangeUserTeam` و `LogoutUserById`.
- پیام سرور: «این کاربر دسترسی‌هایی دارد که شما ندارید؛ به همین دلیل امکان انجام این عملیات روی حساب او را ندارید.»
- همان پیام سرور را در toast نشان دهید. پیام عمومی «دسترسی ندارید» گمراه‌کننده است، چون کاربر خود دسترسی `UserUpdate` را دارد.
- **اختیاری (UX بهتر):** فرانت فعلاً نمی‌تواند از قبل بداند کدام کاربرها «بالاتر» هستند. اگر لازم شد، بگویید تا یک فیلد `canManage` به لیست و جزئیات کاربر اضافه کنیم و دکمه‌ها از قبل غیرفعال شوند.

**غیرفعال/حذف کردن خود:**

- کاربر نمی‌تواند خودش را غیرفعال کند (`UpdateUser` با `isActive: false`) یا حذف کند (`DeleteUser`). سرور ۴۰۰ می‌دهد.
- در صفحه‌ی جزئیات کاربر، اگر `id` با کاربر جاری (`useUserInfoQuery`) یکی بود، سوییچ «فعال» و دکمه‌ی حذف را غیرفعال کنید و tooltip بگذارید: «این کار باید توسط مدیر انجام شود».

## ۶. موارد کوچک

- **حجم درخواست:** سقف هر درخواست ۱۰ مگابایت شد. آپلود تصویر مثل قبل تا ۵ مگابایت است، پس `fileConstraints.js` نیازی به تغییر ندارد.
- **هدرهای امنیتی جدید** روی همه‌ی پاسخ‌ها (`X-Content-Type-Options`، `X-Frame-Options: DENY`، `Referrer-Policy: no-referrer`):
  - روی فرانت اثری ندارند.
  - چاپ PDF از blob URL خود فرانت (`documentOutput.js`) مشمول `X-Frame-Options` نمی‌شود و مثل قبل کار می‌کند.
  - فقط اگر جایی آدرس مستقیم API (مثلاً `File/GetImage?objectKey=x.pdf`) را داخل `<iframe>` باز کنید، دیگر نمایش داده نمی‌شود. اول آن را با axios به blob تبدیل کنید.

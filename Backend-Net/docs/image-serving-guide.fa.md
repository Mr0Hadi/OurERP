# سرو تصاویر: چرا بایت‌ها از خودِ API عبور می‌کنند

**تاریخ:** ۱۴۰۵/۰۶/۱۶ (2026-09-07) · **وضعیت:** پیاده‌سازی و به‌صورت سرتاسری راستی‌آزمایی شد · نسخهٔ انگلیسی: `image-serving-guide.en.md`

## ۱. نشانهٔ مشکل

آپلود کار می‌کرد. حذف هم «کار می‌کرد». اما هر آدرسی که API برمی‌گرداند، در مرورگر فقط
`404 page not found` می‌داد — در حالی که *همان آدرس* با `curl.exe` بدون مشکل باز می‌شد.

دو چیز تشخیص را سخت کرده بود:

- **`DeleteObject` برای کلیدی که وجود ندارد هم `204` برمی‌گرداند.** روی باکتِ واقعی آزمایش شد. پس
  «حذف درست کار می‌کند» هیچ‌وقت شاهدِ چیزی نبود — کلیدِ غلط چیزی را پاک نمی‌کند و باز هم موفقیت
  گزارش می‌شود.
- بدنهٔ پاسخ `404 page not found` بود (متنِ ساده، خروجیِ `http.NotFound` در Go)، **نه** پاسخِ XML
  استانداردِ S3 یعنی `<Code>NoSuchKey</Code>`. این دو از دو سرورِ متفاوت می‌آیند. فقط دومی یعنی
  «فایل موجود نیست».

## ۲. ریشهٔ مشکل

**لبهٔ (edge) فضای ذخیره‌سازیِ لیارا هر درخواستی را که `User-Agent`ش شبیه مرورگر باشد رد می‌کند** و
از روترِ خودش یک `404 page not found` متنی برمی‌گرداند؛ درخواست اصلاً به دروازهٔ S3 نمی‌رسد.

هدر‌به‌هدر روی فایلی که وجودش قطعی بود آزمایش شد — همان آدرس، در همان لحظه:

| `User-Agent` | نتیجه |
|---|---|
| *(بدون)* | `200` تصویر |
| `curl/8.21.0` | `200` تصویر |
| `WMS-Backend/1.0` | `200` تصویر |
| `AppleWebKit/537.36` | `200` تصویر |
| `Mozilla/5.0` | **`404 page not found`** |
| `Mozilla/5.0 (Windows NT 10.0…) Chrome/152…` | **`404 page not found`** |
| `Mozilla/5.0 (X11; Linux…) Firefox/155.0` | **`404 page not found`** |
| `Chrome/152.0.0.0` | **`404 page not found`** |
| `SomeApp Safari/537.36` | **`404 page not found`** |

این مسدودسازی به هیچ‌کدام از گزینه‌هایی که مشکوک به‌نظر می‌رسیدند ربط ندارد:

- سبکِ مسیری (`storage.c2.liara.site/wms/KEY`) **و** سبکِ زیردامنه‌ای (`wms.storage.c2.liara.site/KEY`)
- آدرسِ عمومی **و** آدرسِ امضاشدهٔ درست (`X-Amz-Signature` معتبر است — با curl همان آدرس `200` می‌دهد)
- HTTP/1.1 **و** HTTP/2
- با `Referer` و بدون آن
- چه فایل موجود باشد چه نباشد

پس **هیچ آدرسی که به آن باکت اشاره کند در مرورگر باز نخواهد شد.** کدِ امضا از اول هم غلط نبود.

> دامنهٔ `*.liara.space` (همان که در مستنداتِ خودِ لیارا آمده) از این شبکه اصلاً در دسترس نیست —
> اتصالِ TLS ریست می‌شود — پس گزینهٔ جایگزین نیست.

## ۳. «مگر فرانت نمی‌توانست همان درخواستی را بزند که بک‌اند می‌زند؟»

نه. این مورد مستقیماً از صفحه‌ای روی یک originِ واقعاً جدا (`http://127.0.0.1:5173`) آزمایش شد و به
**دو دلیلِ مستقل** شکست می‌خورد که هیچ‌کدام از سمتِ فرانت قابل رفع نیستند:

```
1. plain fetch()                -> threw: Failed to fetch
2. fetch() + User-Agent: curl   -> threw: Failed to fetch
4. XHR                          -> network error
5. <img src=bucket>             -> FAILED
```

کنسولِ مرورگر:

```
Refused to set unsafe header "User-Agent"
Access to fetch at 'https://storage.c2.liara.site/wms/…' from origin 'http://127.0.0.1:5173'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present.
```

۱. **`User-Agent` یک هدرِ ممنوعه است.** استانداردِ Fetch اجازهٔ ست‌کردنش را به اسکریپت نمی‌دهد و
   `XMLHttpRequest.setRequestHeader` صراحتاً ردش می‌کند. تنها هدری که لیارا رویش فیلتر می‌کند، دقیقاً
   همان هدری است که مرورگر هرگز اجازه نمی‌دهد جاوااسکریپت تغییرش دهد. هیچ راهِ دورزدنی در فرانت
   وجود ندارد — نه fetch، نه XHR، نه axios، نه blob URL، نه service worker.

۲. **حتی اگر می‌شد، CORS جلویش را می‌گیرد.** روتری که به User-Agentهای مرورگری پاسخ می‌دهد، اصلاً
   هدرِ `Access-Control-Allow-Origin` نمی‌فرستد. (دروازهٔ S3 خودش `Origin` را بازتاب می‌دهد — ولی
   مرورگر هیچ‌وقت به آن نمی‌رسد.)

پس چیزی بیرون از مرورگر باید این بایت‌ها را بگیرد، و تنها چیزی که در این سامانه چنین نقشی دارد
خودِ API است. **این تغییر ذاتاً یک تغییرِ بک‌اندی است.**

## ۴. چه چیزی تغییر کرد

### جدید: `GET api/File/GetImage?objectKey=…`

فایل را از دلِ API عبور می‌دهد. AWS SDK آن را سمتِ سرور می‌گیرد، جایی که User-Agent مسدود نیست.

- `[AllowAnonymous]` — یک `<img src>` نمی‌تواند هدرِ `Authorization` بفرستد. این کار چیزی فراتر از
  وضعِ فعلی باز نمی‌کند: باکت هم‌اکنون همین فایل‌ها را به هر درخواست‌کنندهٔ بدونِ احرازِ هویت می‌دهد.
- خروجی `FileResponseDto` و `File(content, contentType)` است — بدون نامِ فایل برای دانلود، تا داخلِ
  `<img>` رندر شود نه اینکه دانلود شود. همان استثنای عمدی از قاعدهٔ `ResponseDto` که اندپوینت‌های
  PDF/بارکد هم دارند.
- کلیدِ ناموجود حالا `NotFoundCustomException` می‌دهد → پاکتِ JSON فارسیِ معمول
  (`تصویر مورد نظر یافت نشد.`) به‌جای ۴۰۴ گنگ و بی‌توضیحِ سرویس‌دهنده.

### `IObjectStorageService`

| عضو | تغییر |
|---|---|
| `DownloadAsync(objectKey, ct)` | **جدید** — فایل را به شکل `StoredFileDto` برمی‌گرداند (بایت‌ها + نوعِ محتوا + نامِ فایل) |
| `GetFixedUrl(objectKey)` | حالا `{PublicBaseUrl}/api/File/GetImage?objectKey=…` برمی‌گرداند — **هاستِ خودمان، نه باکت**. نامش عوض نشد تا هر ۱۵ محلِ فراخوانیِ موجود دست‌نخورده بماند |
| `GetExpirableUrl(objectKey)` | رفتارش عوض نشده (آدرسِ امضاشدهٔ باکت)، ولی حالا مستند شده که **فقط سرور-به-سرور است — هرگز به مرورگر داده نشود** |
| `NormalizeKey(keyOrUrl)` | **برگردانده شد** و گسترش یافت: آدرسِ خودمان با `?objectKey=` را هم می‌شناسد، جایی که کلید در query string است نه در مسیر |

`StoredFileDto` به‌جای نگه‌داشتنِ streamِ باز، در `byte[]` بافر می‌شود — سقفِ آپلود
`MaxImageSizeBytes` (۵ مگابایت) است و `FileResponseDto` هم از قبل `byte[]` حمل می‌کند.

### کلیدِ فایل‌ها: همان نامِ فایلِ کاربر، با رفعِ تکراری

کلیدها خوانا می‌مانند — فهرستِ باکت باید قابلِ تشخیص باشد — پس نامِ فایلِ آپلودشده *همان* کلید است.
دو محافظ روی آن گذاشته شده:

**۱. پسوندِ عددی برای تکراری‌ها.** نامی که از قبل در باکت هست، به‌جای بازنویسی، شماره می‌گیرد:

```
logo.png  ->  logo.png
logo.png  ->  logo-1.png
logo.png  ->  logo-2.png
```

پیش از این، دومین `logo.png` بی‌صدا بایت‌های فایلِ اول را جایگزین می‌کرد — و بعد `imageUrl`ِ
موجودیتِ اول به عکسِ شخصِ دیگری اشاره می‌کرد.

این روش **بررسی‌سپس‌نوشتن است، نه اتمیک.** نوشتنِ شرطیِ S3 (`If-None-Match: *`) توسط این
سرویس‌دهنده *نادیده گرفته می‌شود* — روی باکتِ واقعی آزمایش شد: PUT دوم `200` برگرداند و روی اولی
نوشت — پس امکانِ رزروِ اتمیک وجود ندارد. دو آپلودِ هم‌نام در یک لحظه هنوز می‌توانند تصادف کنند؛
پنجرهٔ خطر یک رفت‌وبرگشت است، در برابرِ رفتارِ قبلی که در *هر* آپلود تصادف می‌کرد. بعد از ۵۰ تلاش،
به‌جای شکستِ آپلود، پسوندِ GUID می‌گیرد: آپلودِ ردشده فایلِ کاربر را از بین می‌برد، ولی کلیدِ زشت
هزینه‌ای ندارد.

**۲. تقلیل به یک قطعهٔ مسیر.** نامِ فایل را کلاینت تعیین می‌کند و عیناً کلید می‌شود، پس نباید بتواند
پیشوندِ دلخواهِ خودش را در باکت انتخاب کند. هر دو جداکنندهٔ مسیر بدونِ توجه به سیستم‌عاملِ میزبان
حذف می‌شوند (نام از یک درخواستِ HTTP می‌آید، نه از فایل‌سیستمِ این ماشین)، به‌همراه کاراکترهای
کنترلی، فاصله‌های ابتدا و انتها و نقطه‌های ابتدا و انتها:

| ارسال‌شده | کلیدِ ذخیره‌شده |
|---|---|
| `../../evil.png` | `evil.png` |
| `products/2026/logo.png` | `logo.png` |
| `C:\Users\alisi\Desktop\photo.png` | `photo.png` |
| `  spaced.png  ` | `spaced.png` |
| *(بعد از پاک‌سازی خالی)* | یک GUID |

یک رفعِ یک‌خطیِ مرتبط در `UploadImageCommandHandler`: بررسیِ فهرستِ پسوندهای مجاز حالا روی نامِ
**trim‌شده** انجام می‌شود. `"  photo.png  "` قبلاً پسوندِ `".png  "` می‌داد، با هیچ‌چیز مطابقت
نمی‌کرد و فایلِ کاملاً سالم را رد می‌کرد.

> کلیدها عمداً قابلِ حدس می‌مانند — این هزینهٔ داشتنِ نام‌های خوانا روی باکتی است که عمومی است.
> بخش ۷.۱ را ببینید.

### مواردی که برگردانده شد، چون اصلِ رفع به آن‌ها وابسته است

- **`ContentType` هنگام آپلود.** روی فایل ذخیره می‌شود و `DownloadAsync` مستقیم پسش می‌دهد، تا
  مرورگر تصویر را نمایش دهد نه اینکه یک `octet-stream` دانلود کند.
- **`NormalizeKey` در همهٔ نقاطِ ذخیره‌سازی** — `Create/Update` برای Product و Customer و Supplier و
  تصاویرِ `ReceivePurchaseCommand`. حالا `ImageUrl` در پاسخ‌های خواندن یک آدرسِ API است؛ بدون این،
  فرانتی که همان مقدار را در آپدیت پس بفرستد، آدرس را داخلِ ستونِ کلید ذخیره می‌کرد.
- **`ObjectKey` در پاسخِ `GetImageUrl`**، در کنارِ `Url`.

`DisablePayloadSigning` عمداً **برگردانده نشد** — `RequestChecksumCalculation.WHEN_REQUIRED` در
ثبتِ DI از قبل مشکلِ قاب‌بندیِ `aws-chunked` را حل می‌کند. آزمایش شد: بدونِ آن هم فایلِ آپلودشده
بایت‌به‌بایت با فایلِ مبدأ یکی است.

### بازبینیِ همهٔ هندلرهایی که با این سرویس کار می‌کنند

هر ۲۸ مصرف‌کننده از نظرِ چرخهٔ آپلود ← ذخیره ← نمایش بررسی شدند. دو مورد خراب بود:

**۱. ضمیمه‌های سند هیچ‌وقت کلیدشان را نرمال نمی‌کردند.** `CreatePurchaseCommand` و
`UpdatePurchaseCommand` و `CreateSaleCommand` و `UpdateSaleCommand` هر چهار تا
`IObjectStorageService` را *تزریق* می‌کردند و بعد هرگز صدایش نمی‌زدند — `attachment.ObjectKey` را
عیناً می‌نوشتند، در حالی که `GetPurchaseDetailQuery` / `GetSaleDetailQuery` همان را از مسیرِ
`GetFixedUrl` می‌خوانند. همهٔ مسیرهای نوشتنِ دیگر در پروژه نرمال‌سازی می‌کردند؛ این چهار تا جا
مانده بودند. اهمیتش این‌جا بیشتر است چون Update فهرستِ ضمیمه‌ها را **یکجا جایگزین می‌کند** (فرانت
همیشه فهرستِ نهایی را می‌فرستد)، پس فرانتی که همان چیزی را که خوانده پس بفرستد به‌راحتی ممکن است
`url` را داخلِ `objectKey` بگذارد — و آن‌وقت ستون یک آدرس با هاستِ درون‌ساخته نگه می‌دارد که به‌محضِ
تفاوتِ `PublicBaseUrl` بینِ محیط‌ها می‌شکند. در هر چهار مورد رفع شد؛ تستِ رگرسیون:
`UpdatePurchase_AttachmentUrlEchoedBack_PersistsTheBareKey`.

**۲. `ScanBarcodeQuery` کلیدِ خام را در فیلدی به نامِ `imageUrl` برمی‌گرداند.** این هندلر اصلاً
سرویسِ ذخیره‌سازی را تزریق نمی‌کرد: `ImageUrl = product.ImageUrl` می‌گذاشت (که همان *کلید* است) و
`ImageKey` را خالی رها می‌کرد — دقیقاً برعکسِ همهٔ مسیرهای خواندنِ دیگر. یک `<img src="logo.png">`
نسبت به originِ *فرانت* حل می‌شود، پس صفحهٔ اسکن تصویرِ شکسته نشان می‌داد در حالی که بقیهٔ صفحه‌ها
درست کار می‌کردند. حالا `ImageKey = product.ImageUrl` و `ImageUrl = GetFixedUrl(...)` است، هماهنگ با
`GetProductDetailQuery`.

بقیه از قبل درست بودند: شش مسیرِ نوشتنِ تصویرِ موجودیت‌ها، عکس‌های `ReceivePurchaseCommand`، هر دو
کوئریِ خواندنِ تصاویرِ رسید، هر چهار کوئریِ لیست و جزئیاتِ محصول/مشتری/تأمین‌کننده، و
`DeleteImage` / `GetImageUrl` / `GetImage` (که درونی نرمال‌سازی می‌کنند).

### پیکربندی

```jsonc
"ObjectStorage": {
  // آدرسِ پایهٔ عمومیِ خودِ این API. آدرسِ تصاویر به «اینجا» اشاره می‌کند، نه به باکت.
  // در هر محیط باید تغییر کند.
  "PublicBaseUrl": "http://localhost:5083"
},
"CorsSettings": {
  "AllowedOrigins": [ "http://localhost:5173", "http://127.0.0.1:5173" ]
}
```

**مقدارِ CORS یک باگِ جداگانه و از قبل موجود بود.** مقدارش `[ "localhost" ]` بود — یک نامِ میزبان،
نه یک origin. در نتیجه `WithOrigins()` با هیچ درخواستی مطابقت نمی‌کرد، هیچ‌وقت هدرِ
`Access-Control-Allow-Origin` فرستاده نمی‌شد، و **همهٔ** فراخوانی‌های مرورگر از سرورِ توسعهٔ Vite
مسدود می‌شدند (شاملِ ورود و لیست‌ها — پروکسیِ Vite وجود ندارد و axios از آدرسِ مطلقِ
`http://localhost:5083/api` استفاده می‌کند). حالا آزمایش شد که هم در preflight و هم در درخواستِ
اصلی هدرِ `Access-Control-Allow-Origin: http://localhost:5173` فرستاده می‌شود.

> **پیش از استقرار، originِ فرانتِ محیطِ عملیاتی را هم به این فهرست اضافه کنید.** همیشه با
> پروتکل + میزبان + پورت.

اگر `PublicBaseUrl` خالی بماند، آدرسِ تصاویر نسبی می‌شود (`/api/File/GetImage?objectKey=…`) که فقط
وقتی کار می‌کند که فرانت از همان originِ API سرو شود.

### تغییرِ نامِ فیلدِ نوشتن به `imageKey` (شکننده)

شش فیلدِ نوشتنِ تصویر هم با هم و هم با سمتِ خواندن ناهماهنگ بودند:

| دستور | قبلاً | حالا |
|---|---|---|
| `CreateProductCommand` | `imageUrl` | `imageKey` |
| `UpdateProductCommand` | `imageObjectKey` | `imageKey` |
| `CreateCustomerCommand` | `imageUrl` | `imageKey` |
| `UpdateCustomerCommand` | `imageUrl` | `imageKey` |
| `CreateSupplierCommand` | `imageUrl` | `imageKey` |
| `UpdateSupplierCommand` | `imageUrl` | `imageKey` |

`imageKey` انتخاب شد نه `imageUrl` (که اکثریت بود)، چون این‌طور **خواندن و نوشتن قرینه می‌شوند**:
هر DTOی خواندن `imageKey` (پایدار) و `imageUrl` (فقط نمایش) برمی‌گرداند، و آن‌که باید پس فرستاده
شود `imageKey` است. فیلدِ نوشتنی به نامِ `imageUrl` که در واقع *کلید* می‌خواهد، دقیقاً همان تله‌ای
است که `NormalizeKey` برای گرفتنش وجود دارد — حالا خودِ نام استفادهٔ درست را آشکار می‌کند، به‌جای
تکیه بر تورِ ایمنی.

سه نگاشتِ Create در AutoMapper حالا صراحتاً ستونِ `ImageUrl` موجودیت را `Ignore()` می‌کنند، تا
کسی دوباره نگاشتِ قراردادی‌ای اضافه نکند که `NormalizeKey` را دور بزند.

`NormalizeKey` هنوز اعمال می‌شود، پس فرستادنِ آدرسِ کامل هم کار می‌کند — ولی قرارداد `imageKey` است.

## ۵. تکلیفِ فرانت‌اند

شکلِ قراردادِ خواندن عوض نشده — DTOها همچنان `imageKey` (پایدار) و `imageUrl` (آمادهٔ نمایش) دارند.
فقط *هاستِ* داخلِ `imageUrl` عوض شده است.

**برای نمایشِ تصویر هیچ کاری لازم نیست.** `<img src>` از CORS معاف است و اندپوینت هم ناشناس است.
از یک originِ جدا آزمایش شد: `IMG: loaded 4096x2341`.

### تغییرِ لازم در فرانت: تغییرِ نامِ فیلدِ نوشتن به `imageKey`

خواندن دست‌نخورده است. فقط کلیدِ payload در شش دستورِ ساخت/ویرایش عوض شده.

```diff
  // useCustomerForm.js / useSupplierForm.js
- imageUrl: imageKey ?? null,
+ imageKey: imageKey ?? null,

  // useProductForm.js — حالا ساخت و ویرایش یکی شدند؛ استثنای imageObjectKey حذف شد
- imageObjectKey: imageKey ?? null,
+ imageKey: imageKey ?? null,
```

پاک‌کردنِ تصویر همچنان `imageKey: null` است. فرستادنِ آدرسِ کامل هم هنوز کار می‌کند
(`NormalizeKey`)، پس اگر جایی از قلم بیفتد خراب نمی‌شود بلکه فقط بهینه نیست — ولی درستش این است که
همه‌جا `imageKey` باشد.

ضمناً حالا که آن‌جا هستید — هرچند ربطی به این تغییر ندارد — تابعِ `objectKeyOf` هنوز کلید را از
pathname آدرس می‌خواند که دیگر نیمهٔ اشتباهی است. پایین‌تر را ببینید.

کامپوننتِ `SignedImage.jsx` از قبل با این قرارداد جور است: مستقیم `imageUrl` را رندر می‌کند و فقط
در `onError` سراغِ `GetImageUrl` می‌رود. آدرس‌های جدید منقضی نمی‌شوند، پس آن مسیر اصلاً فعال نمی‌شود.

**یک ریسکِ خفته که بهتر است رفع شود.** تابعِ `objectKeyOf` در
`src/shared/services/files/objectKey.js` — قرینهٔ `NormalizeKey` در فرانت — کلید را از **pathname**
درمی‌آورد و query string را دور می‌ریزد («کوئری همان امضای منقضی‌شده است»). این فرض دیگر درست نیست:
کلید حالا *داخلِ* query string است. اگر یکی از آدرس‌های جدید به آن داده شود، `api/File/GetImage`
برمی‌گرداند. فعلاً خفته است نه فعال — همهٔ محل‌های فراخوانی کلید پاس می‌دهند نه آدرس (`remoteUrl`
جداگانه نگه داشته می‌شود) — ولی این قرینه با بک‌اند ناهماهنگ شده و باید اول `?objectKey=` را بخواند.

## ۶. راستی‌آزمایی‌های انجام‌شده

- **ریشهٔ مشکل** — تفکیکِ هدربه‌هدر روی فایلِ موجود (جدولِ بخش ۲).
- **ناممکن بودنِ رفع در فرانت** — صفحهٔ واقعی روی originِ جدا؛ `fetch` / `fetch`+UA / XHR / `<img>` همه شکست خوردند (بخش ۳).
- **لایهٔ SDK** — آپلود دقیقاً از مسیرِ کدِ عملیاتی با کلیدهای اَسکی، دارای فاصله، فارسی و `+`/`#`:
  همه `200`، همه بایت‌به‌بایت برابرِ مبدأ، در هر دو سبکِ آدرس‌دهی.
- **رفعِ تکراریِ کلید، روی باکتِ واقعی و از طریقِ خودِ `LiaraObjectStorageService`** — سه بار همان
  نام، خروجی `dedupe-probe.png` / `-1` / `-2` شد و هر سه فایل با بایت‌های متمایزِ خودشان سالم
  خوانده شدند. `../../escaped.png` و `products/2026/nested.png` و `C:\…\windows.png` همگی به‌صورتِ
  نامِ فایلِ ساده و بدونِ جداکننده ذخیره شدند. فایل‌های آزمایشی بعدش حذف شدند.
- **نوشتنِ شرطی** — تأیید شد که `If-None-Match: *` توسط این سرویس‌دهنده رعایت *نمی‌شود* (PUT مقدارِ
  `200` برگرداند و بازنویسی کرد)؛ به همین دلیل رفعِ تکراری بررسی‌سپس‌نوشتن است.
- **مرورگرِ واقعی** — `GET api/File/GetImage` برای کلیدِ ساده، دارای فاصله و فارسی رندر شد؛ کلیدِ
  اشتباه پاکتِ JSON فارسی برگرداند.
- **`<img>` از originِ دیگر** — تصویرِ `4096x2341` بارگذاری شد.
- **CORS** — هدرِ `Access-Control-Allow-Origin` هم در preflight (`204`) و هم در درخواستِ اصلی (`200`) فرستاده شد.
- **بیلد** — `dotnet build WMS.slnx`، بدون خطا.
- **تست‌ها** — ۲۰ تستِ تصویر/ضمیمه سبز است (۷ تا اضافه شد: آدرس باید به API اشاره کند نه باکت و باید
  بایت‌ها را سرو کند؛ آپلودِ هم‌نام باید پسوند بگیرد و هر دو فایل بمانند؛ چهار حالتِ پاک‌سازیِ نامِ
  فایل؛ و یک چرخهٔ بازگشتِ آدرسِ ضمیمه). کلِ مجموعه ۳۵۹ از ۳۶۸؛ آن ۹ شکست از قبل وجود داشته و در CLAUDE.md مستند است — ۸ تا حینِ
  seedِ کاربر روی `IX_Users_PersonelCode` می‌میرند، قبل از اینکه هیچ کدِ تصویری اجرا شود، و نهمی یک
  assertion روی متنِ FluentValidation است.

## ۷. موارد باز (در این تغییر رفع نشده)

۱. **باکت عمومی است و کلیدها عمداً خوانا هستند.** هر کسی بدونِ احرازِ هویت و با یک User-Agent
   غیرمرورگری می‌تواند هر فایلی را بگیرد، و چون کلید همان نامِ اصلیِ فایل است، کلیدها قابلِ حدس‌اند.
   این هزینهٔ پذیرفته‌شدهٔ داشتنِ فهرستِ باکتِ قابلِ تشخیص است. اگر روزی باکت خصوصی شد، `GetImage`
   باید توکنِ امضاشده و منقضی‌شوندهٔ خودش را داشته باشد — صرفاً برگرداندنِ `[Authorize]` همهٔ تصاویر
   را می‌شکند، چون `<img>` نمی‌تواند توکن بفرستد.
۲. **پارامترِ `ImageFolderEnum folder` دریافت و اعتبارسنجی می‌شود ولی استفاده نمی‌شود** — کلیدها تخت
   هستند. برگرداندنِ پیشوندِ `{folder}/` تصادفِ نام بینِ موجودیت‌های مختلف را کم می‌کند، ولی شکلِ
   کلیدهایی را که همین حالا در دیتابیس ذخیره‌اند تغییر می‌دهد.
۳. **کلیدهای واقعیِ لیارا داخلِ `WMS/appsettings.json` کامیت شده‌اند** — مالکِ پروژه در حالِ حذفِ
   آن‌هاست؛ جایشان متغیرهای محیطیِ `ObjectStorage__AccessKey` / `ObjectStorage__SecretKey` است و
   چون در تاریخچهٔ git مانده‌اند باید باطل و از نو ساخته شوند.
۴. **`objectKeyOf` در فرانت** — بخش ۵ را ببینید. عمداً به فرانت واگذار شده؛ همین سند تحویلِ کار است.

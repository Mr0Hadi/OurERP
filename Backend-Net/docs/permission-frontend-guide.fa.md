## ۱. چه چیزی عوض شده است

تا دیروز `[Authorize]` تنها شرط بود: هر کاربر واردشده به هر endpointی دسترسی داشت. از حالا هر endpoint یک **دسترسی (Permission)** مشخص می‌خواهد و نبودنش یعنی **۴۰۳**:

```json
{
  "data": null,
  "message": "شما دسترسی لازم برای انجام این عملیات را ندارید.",
  "responseMessageType": "Danger"
}
```

چند ویژگی که مستقیم روی طراحی فرانت اثر دارد:

- **دسترسی‌ها به شخص داده می‌شوند، نه به واحد یا تیم.** عوض‌شدن دپارتمان یا تیم کاربر هیچ اثری روی دسترسی‌هایش ندارد. اگر جایی در فرانت فرضی بر پایه‌ی «مسئول واحد یعنی دسترسی بیشتر» ساخته‌اید، آن فرض دیگر درست نیست — `OrgRoleEnum` و دسترسی دو محور کاملاً جدا هستند.
- **دسترسی‌ها داخل توکن نیستند.** JWT همچنان فقط `Id`/`FirstName`/`LastName`/`Username` دارد. `expiresAtOf` در `axios.js` که payload توکن را باز می‌کند، **هیچ‌وقت** لیست دسترسی‌ها را آنجا پیدا نخواهد کرد؛ تنها منبع، `GetMyPermissions` است.
- **در عوض، تغییر دسترسی فوری اثر می‌کند.** سرور در هر درخواست از دیتابیس می‌خواند. کاربر لازم نیست دوباره وارد شود یا منتظر انقضای توکن بماند. طرف دیگر سکه: کش فرانت ممکن است کهنه شود (بخش ۶).
- **کاربر غیرفعال‌شده هیچ دسترسی‌ای ندارد**، حتی با توکن هنوز معتبر.

## ۲. endpointهای جدید

| متد | مسیر | دسترسی لازم |
|---|---|---|
| GET | `api/Permission/GetMyPermissions` | — (فقط ورود) |
| GET | `api/Permission/GetPermissionList` | `PermissionView` |
| GET | `api/Permission/GetUserPermissions?userId=12` | `PermissionView` |
| PUT | `api/Permission/UpdateUserPermissions` | `PermissionManage` |

شکل پاسخ‌ها در api-guide بخش ۳د است. دو نکته‌ی مهم:

**الف) روی `name` شرط بگذارید، نه روی عدد.** هر دسترسی هم عدد دارد هم نام (`{ "permission": 94, "name": "SaleShip", "title": "ارسال کالا به مشتری" }`). عددها قرارداد دائمی‌اند و هرگز عوض نمی‌شوند، ولی `can("SaleShip")` در ریویو خوانا است و `can(94)` نیست. `GetMyPermissions` عمداً آرایه‌ی آماده‌ی `permissionNames` را هم می‌فرستد.

**ب) `GetUserPermissions` علاوه بر لیست کاربر، خودِ کاتالوگ گروه‌بندی‌شده را هم برمی‌گرداند** (`permissionGroups`)، تا صفحه‌ی ویرایش با یک درخواست هم چک‌باکس‌ها را بسازد هم تیک‌ها را بزند.

## ۳. `usePermissionsQuery` و helper

پیشنهاد: کنار `useUserInfoQuery` در `src/features/auth/services/`.

```js
// services/queries.js
export function useMyPermissionsQuery() {
  const isAuthenticated = useAuthStore((s) => s.isAuthenticated);

  return useQuery({
    queryKey: authKeys.myPermissions(),
    queryFn: getMyPermissions,
    enabled: isAuthenticated,
    staleTime: 5 * 60 * 1000,
  });
}

// hooks/usePermission.js
export function usePermission() {
  const { data, isPending } = useMyPermissionsQuery();
  const names = useMemo(() => new Set(data?.permissionNames ?? []), [data]);

  return {
    isPending,
    can: (permission) => names.has(permission),
    canAny: (...permissions) => permissions.some((p) => names.has(p)),
  };
}
```

**`isPending` را جدی بگیرید.** تا وقتی پاسخ نیامده، `can()` برای همه‌چیز `false` است. اگر منو یا گارد مسیر این حالت را از «دسترسی ندارد» تشخیص ندهد، کاربر برای یک لحظه منوی خالی یا صفحه‌ی «دسترسی ندارید» می‌بیند — دقیقاً همان مشکلی که `hasHydrated` در `authStore` برای توکن حل می‌کند.

**در `authStore` نگذاریدش.** همان دلیلی که آنجا برای هویت کاربر نوشته شده اینجا قوی‌تر است: کپیِ دسترسی‌ها در `localStorage` بعد از هر تغییر توسط ادمین کهنه می‌ماند و هیچ‌چیز باطلش نمی‌کند — در حالی که سرور همان لحظه رفتارش را عوض کرده است.

## ۴. منو و مسیرها

**منو:** `src/shared/constants/navigationData.js` امروز یک ساختار ثابت است. به هر آیتم یک فیلد دسترسی اضافه کنید و در `AppSidebar.jsx` قبل از پاس‌دادن به `NavMain` فیلتر کنید:

```js
{ title: "فروش", url: ROUTES.SALES, permission: "SaleView",
  items: [
    { title: "ارسال کالا", url: ..., permission: "SaleShip" },
  ] }
```

آیتم والدی که همه‌ی فرزندانش فیلتر شده‌اند باید خودش هم حذف شود، وگرنه منوی بازشونده‌ی خالی می‌ماند.

**مسیرها:** فیلتر منو کافی نیست — کاربر می‌تواند URL را مستقیم تایپ کند یا بوکمارک داشته باشد. در `src/app/routes/routers.jsx` یک wrapper کنار `AppLayout` بگذارید که مثل `hasHydrated` عمل کند: تا `isPending` است چیزی رندر نکند، بعد اگر `can()` برقرار نبود به صفحه‌ی «دسترسی ندارید» بفرستد (نه به لاگین — کاربر واردشده است).

**و یادتان باشد این‌ها فقط UX هستند.** بررسی واقعی سمت سرور است؛ هیچ‌وقت مخفی‌بودن دکمه را محافظت حساب نکنید.

## ۵. مدیریت ۴۰۳ در `axios.js`

امروز `interceptors.response` فقط `status === 401` را جدا مدیریت می‌کند و بقیه‌ی خطاها با `messageOf(error)` به `error.message` تبدیل و در toast نشان داده می‌شوند. برای ۴۰۳ این رفتار **کار می‌کند** (پیام فارسی سرور درست نمایش داده می‌شود) ولی کافی نیست:

- **۴۰۳ را وارد مسیر refresh نکنید.** الان هم نمی‌شود چون شرط روی ۴۰۱ است؛ فقط هنگام ویرایش این فایل حواستان باشد. رفرش‌کردن توکن برای ۴۰۳ بی‌فایده است: توکن سالم است، دسترسی نیست.
- **۴۰۳ نباید باعث logout شود.** کاربر معتبر است.
- توصیه: در این interceptor روی ۴۰۳ یک flag بگذارید (مثلاً `error.isForbidden = true`) تا صفحه‌ها بتوانند به‌جای toast، حالت «دسترسی ندارید» را نشان دهند.

**یک تغییر جانبی:** پاسخ ۴۰۱ که تا دیروز **بدنه‌ی خالی** داشت، حالا همان پوشش `ResponseDto` را دارد. `isEnvelope`/`messageOf` با آن مشکلی ندارند و منطق refresh دست‌نخورده کار می‌کند؛ فقط اگر جایی بر «بدنه‌ی ۴۰۱ خالی است» حساب شده بود، دیگر درست نیست.

## ۶. صفحه‌ی مدیریت دسترسی‌ها

جای طبیعی‌اش کنار صفحه‌ی کاربران است (`src/features/employees/`). گردش کار:

1. `GET api/Permission/GetUserPermissions?userId=…` → هم کاتالوگ گروه‌بندی‌شده، هم تیک‌های فعلی.
2. رندر چک‌باکس‌ها به تفکیک `groupTitle`.
3. `PUT api/Permission/UpdateUserPermissions` با **لیست نهایی کامل** — قرارداد جایگزینی کامل است، مثل `attachments` و `paymentDetails`. آرایه‌ی خالی یعنی همه‌چیز گرفته شود.

نکته‌های رفتاری که باید در UI دیده شوند:

- **بعد از موفقیت، اگر کاربر هدف خودِ کاربر واردشده است، `queryKey` مربوط به `GetMyPermissions` را invalidate کنید** وگرنه منوی خودش تا انقضای `staleTime` کهنه می‌ماند.
- کاربر **نمی‌تواند دسترسی «مدیریت دسترسی‌های کاربران» را از خودش بگیرد** — ۴۰۰ با پیام صریح. بهتر است همان چک‌باکس در UI هم برای خود کاربر غیرفعال شود تا خطا نگیرد.
- پاسخ `{ userId, addedCount, removedCount }` است؛ برای toast «۳ دسترسی اضافه، ۱ حذف شد» کافی است.
- **الگوی واحد (۲۰۲۶-۰۹-۲۳):** `GetDepartmentPermissionTemplate?departmentId=…` الگوی پیشنهادیِ واحد را می‌دهد. در صفحه‌ی کارمند، الگوی واحدِ *انتخاب‌شده در فرم* (نه واحد ذخیره‌شده) پیشنهاد می‌شود تا هنگام جابه‌جایی کارمند، ادمین همان لحظه الگوی مقصد را ببیند. اعمال الگو فقط چک‌باکس‌ها را عوض می‌کند؛ ذخیره همچنان `UpdateUserPermissions` است. پیاده‌سازی فعلی فرانت: صفحه‌های «سطح دسترسی ← دسترسی کارمندان» (`/access/users/:id`) و «الگوهای واحدها» (`/access/templates/:id`) به شکل فهرست/جزئیات؛ در صفحه‌ی کارمند و واحد فقط یک کارت خلاصه هست و ویرایش دسترسی کارمند در یک Sheet باز می‌شود تا واحدِ ذخیره‌نشده‌ی فرم حفظ شود.
- کاتالوگی که سرور برمی‌گرداند **ممکن است کامل نباشد**: سرور فقط دسترسی‌هایی را نشان می‌دهد که خودِ کاربر درخواست‌دهنده اجازه‌ی دیدن‌شان را دارد. پس **هیچ‌وقت لیست دسترسی‌ها را در فرانت هاردکد نکنید** و همیشه از همین پاسخ بسازید؛ در غیر این صورت چک‌باکسی نمایش می‌دهید که ارسالش ۴۰۰ می‌گیرد.

## ۷. دو endpoint که رفتارشان فراتر از افزودن گارد عوض شد

- **`POST api/Account/Logout`** حالا نیاز به توکن دارد. در عمل تغییری نمی‌کند چون هندلرش از قبل هم شناسه‌ی کاربر واردشده را می‌خواند و بدون توکن خطا می‌داد. ولی `useLogoutMutation` که عمداً `onSettled` استفاده می‌کند (و نه `onSuccess`) دقیقاً برای همین حالت درست نوشته شده — دست نخورد.
- **`POST api/Account/LogoutUserById`** — خارج‌کردن اجباری کاربر دیگر — تا دیروز **برای همه، حتی بدون توکن** باز بود؛ حالا `UserUpdate` می‌خواهد.

تا وقتی هیچ‌کس `PermissionManage` نداشته باشد، از داخل سامانه هیچ دسترسی‌ای قابل دادن نیست و **همه‌ی صفحه‌ها ۴۰۳ می‌دهند**. اگر موقع تست با «همه‌چیز ۴۰۳ شد» مواجه شدید، اول همین را چک کنید.

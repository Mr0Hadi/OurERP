# قرارداد ساختار سازمانی — چه چیزی در بکند باید تغییر کند

**تاریخ:** ۱۴۰۵/۰۶/۰۳ (۲۰۲۶-۰۸-۲۵) · **وضعیت فرانت:** انجام‌شده، روی برنچ `feat/employees-management`

## چرا این سند

فرانت فیچرهای «مدیریت کارمندان» و «ساختار سازمانی» (واحدها و تیم‌ها) را ساخته است. بخش زیادی از آن روی API های موجود بکند سوار می‌شود، ولی فرانت در چند نقطه از بکند جلوتر است — فیلدهایی که مدل بکند ندارد و endpoint هایی که وجود ندارند.

این سند دقیقاً می‌گوید بکند چه کاری باید انجام دهد. برادرِ [`frontend-enum-contract.fa.md`](./frontend-enum-contract.fa.md) است و همان ساختار را دارد.

| بخش | موضوع | کار لازم | حجم |
|---|---|---|---|
| ۱ | چیزهایی که هماهنگ‌اند | هیچ | — |
| ۲ | `GetUserList` | endpoint جدید | متوسط |
| ۳ | `DepartmentId`/`TeamId` در `CreateUser`/`UpdateUser` | **باگ** — اصلاح لازم | کم |
| ۴ | `DeputyId` روی `Department` و `Team` | ستون + migration | کم |
| ۵ | سید کردن واحدها | داده‌ی اولیه | کم |
| ۶ | `GetRoleList` | endpoint جدید | کم |
| ۷ | نکات پراکنده | چند اصلاح کوچک | کم |

## ۱. هماهنگ — کاری لازم نیست

این‌ها در بکند وجود دارند و فرانت دقیقاً روی همان‌ها سوار شده:

| موضوع | endpoint / موجودیت | فایل فرانت |
|---|---|---|
| CRUD واحد | `api/Department/*` | `features/organization/departments/services/api-v1.js` |
| CRUD تیم | `api/Team/*` | `features/organization/teams/services/api-v1.js` |
| ساخت/ویرایش/حذف کارمند | `api/User/CreateUser`, `UpdateUser`, `DeleteUser` | `features/employees/services/api-v1.js` |
| جزئیات کارمند برای فرم ویرایش | `api/User/GetUserUpdate` | همان |
| خروج اجباری کاربر توسط ادمین | `api/Account/LogoutUserById` | همان |
| رابطه‌ی `User → Department → Team` | جدول‌های موجود | — |
| مدیر واحد و تیم (`HeadId`) | جدول‌های موجود | — |

> **درباره‌ی «نقش» و «واحد»:** این دو در بکند درست از هم جدا شده‌اند و فرانت هم همین تفکیک را رعایت می‌کند. `Role` سطح دسترسی است (`Admin`/`User`) و `Department` واحد سازمانی. توجه: شش موردی که در گفت‌وگو به‌عنوان «نقش» نام برده شد (تامین، فروش، انبارداری، حسابداری، فناوری) در واقع **واحد**اند، نه نقش.

## ۲. `GetUserList` وجود ندارد — endpoint جدید لازم است

`UserController` هیچ endpoint فهرستی ندارد. صفحه‌ی «مدیریت کارمندان» بدون آن اصلاً کار نمی‌کند.

فرانت امضای زیر را فرض کرده — دقیقاً هم‌شکل با `GetTeamList` و `GetDepartmentList` که خودتان نوشته‌اید:

### `GET api/User/GetUserList`

**پارامترهای Query:**

| پارامتر | نوع | توضیح |
|---|---|---|
| `page` | `int` | پیش‌فرض ۱ |
| `take` | `int` | پیش‌فرض ۱۰ |
| `fullName` | `string?` | جست‌وجو در نام، نام‌خانوادگی، نام کاربری و کد پرسنلی |
| `roleId` | `int?` | فیلتر نقش |
| `departmentId` | `int?` | فیلتر واحد |
| `teamId` | `int?` | فیلتر تیم |
| `isActive` | `bool?` | `null` یعنی همه |

**`data` خروجی** (مثل بقیه‌ی لیست‌ها):

```json
{
  "userList": [
    {
      "id": 5,
      "firstName": "سارا",
      "lastName": "محمدی",
      "username": "sara_mohammadi",
      "personelCode": "1002",
      "roleId": 2,
      "roleName": "User",
      "departmentId": 3,
      "departmentName": "واحد فروش",
      "teamId": 1,
      "teamName": "تیم ۱ فروش",
      "isActive": true,
      "createdAt": "2026-01-01T00:00:00"
    }
  ],
  "page": { "page": 1, "pageCount": 3, "take": 10, "total": 27 }
}
```

`departmentName` و `teamName` را از join بدهید — فرانت برای نمایش به نام نیاز دارد و گرفتن جداگانه‌ی آن‌ها یعنی N+1 درخواست.

## ۳. ⚠️ باگ: `CreateUser`/`UpdateUser` واحد و تیم را نمی‌گیرند

این مهم‌ترین بند این سند است.

`User` در دیتابیس این دو ستون را دارد و **هر دو `int` غیرقابل‌null هستند**:

```csharp
public int DepartmentId { get; set; }
public int TeamId { get; set; }
```

ولی `CreateUserCommand` و `UpdateUserCommand` هیچ‌کدام این فیلدها را ندارند و `MappingProfile` هم مقداردهی‌شان نمی‌کند. نتیجه: **هر کاربری که از طریق API ساخته شود، `DepartmentId = 0` و `TeamId = 0` می‌گیرد** — یا FK می‌شکند، یا رکوردی می‌ماند که به هیچ واحدی تعلق ندارد.

### کار لازم

۱. به `CreateUserCommand` اضافه کنید:
```csharp
public int DepartmentId { get; set; }
public int? TeamId { get; set; }
```

۲. همین دو را به `UpdateUserCommand` هم اضافه کنید و در handler ست کنید.

۳. اعتبارسنجی: `DepartmentId` باید وجود داشته باشد؛ اگر `TeamId` داده شد، تیم باید **متعلق به همان واحد** باشد. فرانت این قاعده را در UI رعایت می‌کند (انتخابگر تیم فقط تیم‌های واحدِ انتخاب‌شده را نشان می‌دهد) ولی سرور هم باید ببندد.

### درباره‌ی `TeamId`

فرانت فرض کرده **تیم اختیاری است** ولی واحد اجباری — چون مدیر یک واحد لزوماً عضو هیچ تیمی نیست. ولی `User.TeamId` الان `int` غیرقابل‌null است.

پیشنهاد: `TeamId` را `int?` کنید. اگر با این موافق نیستید و تیم باید همیشه اجباری باشد، بگویید تا فرانت آن را اجباری کند — ولی آن‌وقت باید برای مدیران واحد یک تیمِ ساختگی تعریف شود که تمیز نیست.

## ۴. `DeputyId` وجود ندارد — ستون جدید لازم است

نه `Department` و نه `Team` فیلد معاون ندارند؛ فقط `HeadId`.

طبق نیاز کسب‌وکار، **هر واحد و هر تیم یک مدیر و یک معاون دارد**.

### کار لازم

به هر دو موجودیت اضافه کنید، دقیقاً هم‌شکل با `HeadId` موجود:

```csharp
public int? DeputyId { get; set; }
public User? Deputy { get; set; }
```

و در `WMSDbContext.OnModelCreating`، هم‌شکل با نگاشت `Head`:

```csharp
modelBuilder.Entity<Department>()
    .HasOne(d => d.Deputy)
    .WithMany()
    .HasForeignKey(d => d.DeputyId)
    .OnDelete(DeleteBehavior.Restrict);
```

سپس `DeputyId`/`DeputyName` را به این‌ها اضافه کنید: `CreateDepartmentCommand`، `UpdateDepartmentCommand`، `CreateTeamCommand`، `UpdateTeamCommand`، `DepartmentDto`، `DepartmentListDto`، `TeamDto`، `TeamListDto`.

اعتبارسنجی پیشنهادی: معاون نباید همان مدیر باشد.

### وضعیت فعلی فرانت

فیلد «معاون» در فرم واحد و تیم **ساخته شده ولی غیرفعال است** و در payload ارسال **نمی‌شود**. یک پیام زرد کنارش توضیح می‌دهد که در انتظار بکند است.

این حالت عمدی است: اگر فیلد را حذف می‌کردیم، بعداً باید فرم دوباره طراحی می‌شد؛ اگر فعال می‌گذاشتیم، کاربر معاون انتخاب می‌کرد و سرور بی‌صدا دورش می‌ریخت — یعنی UI دروغ می‌گفت.

**بعد از اضافه‌شدن ستون، تغییر لازم در فرانت فقط دو نقطه است:**
- `features/organization/components/OrgLeadershipForm.jsx` — برداشتن `disabled` و پیام زرد
- `useDepartmentForm.js` / `useTeamForm.js` — افزودن `deputyId` به payload

## ۵. واحدها سید نشده‌اند

جدول `Department` خالی است. تا وقتی ردیفی نداشته باشد، انتخابگرِ واحد در فرم کارمند خالی می‌ماند و کاربر گیر می‌کند.

فرانت فعلاً یک fallback دارد (`shared/domain/enums/department.js`) که وقتی سرور چیزی برنگرداند، همین شش واحد را نشان می‌دهد. **این یک تور ایمنی است، نه قرارداد** — داده‌ی سرور همیشه برنده است.

### شناسه‌های پیشنهادی

اگر همین شناسه‌ها سید شوند، فرانت و بکند از روز اول هماهنگ‌اند و به نگاشت نیازی نیست:

| `Id` | `Name` |
|---|---|
| `1` | ادمین کل |
| `2` | واحد تامین |
| `3` | واحد فروش |
| `4` | واحد انبارداری |
| `5` | واحد حسابداری |
| `6` | واحد فناوری |

اگر شناسه‌های دیگری سید کردید مشکلی نیست — فقط بگویید تا fallback فرانت به‌روز شود.

این مورد قبلاً در [`api-guide.fa.md` بخش ۱۶](./api-guide.fa.md) هم ذکر شده. `Role` یک جدول است ولی هیچ endpoint ای برای خواندنش نیست.

## ۷. نکات پراکنده

- **`fisrtName` غلط املایی است.** `CreateUserCommand.FisrtName` — فرانت همین را می‌فرستد چون قرارداد فعلی است. اگر اصلاحش کردید، خبر بدهید (تغییرِ یک خط در فرانت است).

- **⚠️ `IsEnglishText` نقطه را رد می‌کند ولی نمونه‌های سند نقطه دارند.** الگوی `Validation.IsEnglishText` این است:
  ```
  ^[A-Za-z\s\d_-]+$
  ```
  که `.` را مجاز نمی‌داند. ولی نمونه‌های `api-guide.fa.md` بخش ۳ `ali.rezaei` و `sara.m` هستند — یعنی **سند با کد تناقض دارد و آن نمونه‌ها با validator فعلی رد می‌شوند.**

  فرانت با *کد* هماهنگ شده (نقطه ممنوع)، چون در غیر این صورت کاربر فرم را سبز می‌بیند و بعد ۴۰۰ می‌گیرد. اگر نقطه باید مجاز باشد، regex را به `^[A-Za-z\d._-]+$` تغییر دهید و خبر بدهید.

- **ادمین نمی‌تواند رمز کارمند دیگر را عوض کند.** `ChangePassword` فقط روی کاربرِ جاریِ توکن کار می‌کند و رمز قبلی می‌خواهد. اگر «ریست رمز توسط ادمین» لازم است، یک endpoint جدید (مثلاً `POST api/User/ResetUserPassword`) می‌خواهد. فعلاً فرانت کارت رمز عبور را فقط در صفحه‌ی *ثبت* نشان می‌دهد.

- **جایگاه (مدیر/معاون/عضو) نباید روی `User` ذخیره شود.** فرانت آن را از `Department.HeadId`/`Team.HeadId` *مشتق* می‌کند. اگر ستونی روی `User` اضافه شود، دو منبع حقیقت داریم که می‌توانند ناهم‌خوان شوند.

- **`DeleteDepartment` و `DeleteTeam` وابستگی را چک نمی‌کنند.** حذف نرمِ واحدی که هنوز تیم دارد، تیم‌هایش را بی‌صاحب می‌گذارد (و `Team.DepartmentId` غیرقابل‌null است). فرانت این را در UI می‌بندد، ولی سرور هم بهتر است ۴۰۰ بدهد.

## ۸. سرپرست/معاونِ واحد و تیم اکنون با `User.DepartmentId`/`TeamId` همگام است (۱۴۰۵/۰۶/۱۶ — ۲۰۲۶-۰۹-۰۷)

باگ گزارش‌شده: کاربری را در ویرایش کاربر عضو «واحد الف» می‌کردید؛ بعد در صفحه‌ی واحد/تیم همان کاربر را به‌عنوان سرپرست یا معاون تعیین می‌کردید — رکورد خودِ کاربر (`DepartmentId`/`TeamId`) تغییری نمی‌کرد ولی در صفحه‌ی واحد/تیم به‌عنوان سرپرست نمایش داده می‌شد؛ یعنی دو منبع داده ناهم‌خوان بودند.

### رفتار جدید بکند

`CreateTeamCommand`/`UpdateTeamCommand`/`CreateDepartmentCommand`/`UpdateDepartmentCommand` اکنون **اعتبارسنجی می‌کنند، نه اینکه کاربر را خودکار جابه‌جا کنند**:

- `HeadId`/`DeputyId` باید متعلق به **همان واحدِ** تیم/دپارتمان باشد (یعنی `User.DepartmentId` برابر با `DepartmentId` تیم یا با `Id` دپارتمان). در غیر این صورت `400` با پیام «سرپرست/معاون باید عضو همین دپارتمان باشد» برمی‌گردد.
- روی `CreateDepartmentCommand`: چون دپارتمان تازه دارد ساخته می‌شود، **هیچ کاربری از قبل نمی‌تواند عضوش باشد** — پس فرستادن `headId`/`deputyId` روی ایجاد همیشه رد می‌شود (۴۰۰). ترتیب درست: اول دپارتمان را بدون سرپرست بسازید، کاربر را به آن منتقل کنید (`UpdateUser` یا `ChangeUserTeam`)، سپس با `UpdateDepartmentCommand` سرپرست را تعیین کنید.
- روی `CreateTeamCommand`: چون دپارتمانِ تیم از قبل وجود دارد، تعیین سرپرست/معاون از همان ابتدا ممکن است — به شرطی که آن کاربر از قبل عضو همان دپارتمان باشد.
- وقتی کسی سرپرست/معاونِ جدیدِ یک تیم یا دپارتمان می‌شود، هر نقش سرپرستی/معاونتِ قبلی‌اش (در هر تیم/دپارتمان دیگر) پاک می‌شود (`IOrgRoleService.ReleaseAllRolesAsync`) — همان‌قاعده‌ای که از قبل روی `ChangeUserTeamCommand`/`DeleteUserCommand` بود، یعنی «هر کاربر حداکثر یک سِمَتِ تیمی و یک سِمَتِ دپارتمانی».

این یعنی جهت هم‌گام‌سازی **صریح و یک‌طرفه** است: عضویتِ کاربر (`User.DepartmentId`/`TeamId`) منبعِ حقیقت است؛ سرپرست/معاونِ تیم و دپارتمان فقط می‌تواند از میان اعضای موجود انتخاب شود، نه برعکس. این با بند ۷ همین سند («جایگاه نباید روی `User` ذخیره شود») سازگار است — چیزی به مدل `User` اضافه نشده، فقط جهتِ اعتبارسنجی درست شده.

### کاری که فرانت باید انجام دهد (فقط مستندسازی، تغییری در بکند برایش داده نشده)

1. **فرم تعیین سرپرست/معاونِ تیم و دپارتمان باید لیستِ کاربران را به اعضای همان واحد محدود کند** (یعنی دقیقاً همان چیزی که سرور اکنون اجرا می‌کند) — وگرنه کاربر گزینه‌ای را انتخاب می‌کند که سرور با ۴۰۰ رد می‌کند. فیلتر روی `departmentId` تیم/دپارتمان در `GetUserList` (بند ۲) همین الان هم پشتیبانی می‌شود.
2. **فرم ایجاد دپارتمان باید فیلد سرپرست/معاون را اصلاً نشان ندهد** (نه فقط غیرفعال) — چون سرور آن را همیشه رد می‌کند؛ سرپرست فقط بعد از ایجاد، از صفحه‌ی ویرایش دپارتمان قابل‌تعیین است.
3. **در فرم ویرایش کاربر، وقتی واحد (`departmentId`) عوض می‌شود، لیست تیم‌های قابل‌انتخاب باید فوراً به تیم‌های همان واحد محدود شود** (و اگر تیمِ فعلاً انتخاب‌شده به واحد جدید تعلق ندارد، پاک شود) — این قانون از قبل روی سرور بسته است (`CreateUserCommand`/`UpdateUserCommand`/`ChangeUserTeamCommand`: تیم باید `DepartmentId` برابر با دپارتمانِ درخواست داشته باشد) ولی فرانت هنوز این را در UI اعمال نمی‌کند، پس کاربر می‌تواند تیمی از واحد قبلی را انتخاب کند و با ۴۰۰ مواجه شود.
